## 1. Немного о сети

**Пакеты.** Всё, что компьютер отправляет в сеть, режется на небольшие куски, пакеты. На каждом пакете написано, откуда он (IP отправителя) и куда (IP получателя). Можно представить конверт с адресами.

**Интерфейсы** — «двери», через которые пакеты выходят из компьютера. Посмотреть их список можно командой `ifconfig -l`:
- `en0`, `en1` — настоящие сетевые карты (Wi-Fi, Ethernet);
- `lo0` — loopback, «дверь сама в себя», для общения программ внутри компьютера;
- `utun0`, `utun1`… — **виртуальные** интерфейсы. Физически их нет, их создают программы, в том числе VPN.

**Как работает VPN.** VPN-клиент создаёт интерфейс, например `utun6`, и говорит системе: «весь интернет отправляй через `utun6`». Пакет, попавший в `utun6`, клиент шифрует, кладёт в новый конверт с адресом VPN-сервера и отправляет уже через настоящую дверь `en0`. Сервер распаковывает его и отправляет дальше по назначению.

```
программа → utun6 (туннель) → VPN-клиент шифрует → en0 → VPN-сервер → сайт
```

**Утечка.** Если VPN отвалился, `utun6` исчезает. macOS «услужливо» отправляет пакеты напрямую через `en0`, то есть с вашим настоящим IP. Kill switch нужен, чтобы этого не случилось.

## 2. Что такое pf

**pf (Packet Filter)** — файрвол, встроенный в ядро macOS. Он смотрит на **каждый** пакет на входе и выходе и сверяет его со списком правил: пропустить (`pass`) или заблокировать (`block`).

Как читается правило (на примере реальных строк скрипта):

```
pass  quick on lo0 all no state
│     │     │       │   └─ не запоминать соединение (ниже)
│     │     │       └─ любые пакеты
│     │     └─ на интерфейсе lo0
│     └─ если подошло, дальше не проверять
└─ пропустить
```

```
pass out quick to 203.0.113.10 no state    # исходящие к серверу VPN
block return out quick all                  # все остальные исходящие — отклонить
```

Ключевые понятия:
- **Порядок важен.** Правила проверяются сверху вниз. Слово `quick` значит «подошло — решение принято, остальное не смотрим». Поэтому в скрипте сначала идут разрешения, а в самом конце запрет всего остального.
- **`out` / `in`** — направление: исходящий или входящий трафик.
- **`block return`** — отказать и сразу сообщить программе «нельзя», чтобы браузер выдал ошибку, а не висел минуту. **`block drop`** — молча выбросить пакет.
- **`no state`.** Обычно pf «запоминает» разрешённые соединения и дальше пропускает их без проверки. Скрипт это отключает, и каждый пакет проверяется по правилам. Зачем: в момент включения pf ничего не знает об уже открытых соединениях и мог бы их порвать. Без запоминания он просто смотрит, через какой интерфейс и куда идёт пакет.
- **Макросы.** `tun_ifs = "{ utun0, utun1, ... }"` — переменная внутри конфига pf. Потом `$tun_ifs` подставляет весь список.

**`pfctl`** — команда для управления pf из терминала. Скрипт использует такие её варианты:

| Команда | Что делает |
|---|---|
| `pfctl -E` | включить pf и получить «токен» |
| `pfctl -X <токен>` | вернуть токен (выключить pf, если он больше никому не нужен) |
| `pfctl -a <раздел> -f <файл>` | загрузить правила из файла в раздел |
| `pfctl -a <раздел> -F rules` | очистить правила раздела |
| `pfctl -a <раздел> -sr` | показать правила раздела |
| `pfctl -n ...` | ничего не применять, только проверить синтаксис |
| `pfctl -F states` | забыть все запомненные соединения |

## 3. Как pf устроен в macOS

**pf по умолчанию выключен**, но системный конфиг `/etc/pf.conf` при загрузке всё равно загружается. Он почти пустой, в нём главное — строка:

```
anchor "com.apple/*"
```

**Anchor** — «раздел» правил, как папка. Эта строка значит: «проверь правила во всех подразделах `com.apple/...`». Туда macOS сама добавляет свои правила, например для AirDrop или общего доступа к интернету.

Скрипт кладёт свои правила в подраздел `com.apple/000.vpn_killswitch`. Отсюда три плюса:
- системный конфиг не трогается вообще;
- правила начинают действовать сразу после загрузки и исчезают сразу после очистки, поэтому перезагрузка не нужна;
- `000.` в начале имени: подразделы проверяются по алфавиту, так что наши правила идут раньше системных.

**Токены.** pf могут включать сразу несколько программ. Чтобы одна не выключила его под другой, `pfctl -E` выдаёт номерок, а `pfctl -X номерок` его возвращает. pf выключается, только когда возвращены все номерки. Скрипт хранит свой номерок в файле и при `--stop` возвращает только его.

**`/var/run`** — папка для временных служебных файлов, она очищается при перезагрузке. Правила pf тоже живут только в памяти. Поэтому после перезагрузки kill switch выключен, и состояние скрипта остаётся согласованным.

## 4. Что делает скрипт, по шагам

### Разбор аргументов (конец файла)
1. Перебирает аргументы в цикле `while`. Конструкция `case` смотрит, что пришло: `--start`, `--stop`, `--status`, `--allow-lan` или IP-адрес.
2. IP проверяется функциями `is_ipv4` / `is_ipv6`. Например, `300.1.1.1` будет отвергнут. IP через запятую разбиваются на отдельные.
3. Проверяются бессмысленные комбинации: `--start` без IP, `--stop` с IP, два действия сразу.
4. **sudo.** Если скрипт запущен не от root (`$EUID` не равен 0), он перезапускает сам себя через `sudo` с теми же аргументами. pf могут менять только администраторы.
5. Вызывает нужную функцию: `start`, `stop` или `status`.

### `--start` (функция `start`)
1. Создаёт папку `/var/run/vpn-killswitch/` с доступом только для root.
2. **Генерирует правила.** Функция `gen_rules` выводит текст конфига pf с подставленными IP, а скрипт записывает его в `rules.conf`. По сути она печатает готовый файл.
3. **Проверка без применения:** `pfctl -n ...`. Если в правилах ошибка, скрипт останавливается и ничего не ломает.
4. Проверяет, что системная строка `anchor "com.apple/*"` на месте. Если кто-то её удалил, перезагружает `/etc/pf.conf`, иначе наш раздел никто бы не проверял.
5. Загружает правила в раздел `com.apple/000.vpn_killswitch`.
6. Если своего токена ещё нет, включает pf через `pfctl -E` и сохраняет токен в файл. При повторном `--start` второй токен не берётся, просто обновляются правила.
7. Сбрасывает запомненные соединения (`pfctl -F states`). Если pf был включён кем-то раньше, соединения, открытые мимо VPN, могли бы продолжать работать, а так они обрываются.

Итоговые правила (упрощённо):
```
pass  на lo0                          # внутри компьютера
pass  на utun*/ipsec*/ppp*/tun*       # всё, что в туннеле
pass  к/от IP VPN-сервера             # чтобы туннель мог подняться
pass  DHCP (порты 67/68)              # получить адрес от роутера
pass  к/от локальной сети             # только с --allow-lan
block всё остальное
```

Как это ловит обрыв VPN: пока VPN работает, пакеты идут в `utun` и проходят. Когда VPN упал, macOS шлёт пакет в `en0` на какой-нибудь google.com. Ни одно разрешающее правило не подходит, срабатывает последнее, `block`.

### `--stop` (функция `stop`)
1. Очищает наш раздел (`pfctl -a ... -F rules`), и ограничения мгновенно исчезают.
2. Возвращает токен (`pfctl -X`). Если pf больше никому не нужен, он выключается.
3. Удаляет папку `/var/run/vpn-killswitch/`.

### `--status`
Показывает правила из нашего раздела. Если раздел пуст, kill switch выключен.

## 5. Bash-конструкции, которые встретятся в коде

| Конструкция | Значение |
|---|---|
| `set -eo pipefail` | при любой ошибке скрипт сразу останавливается, а не продолжает вслепую |
| `имя() { ... }` | функция: именованный кусок кода, вызывается как команда |
| `$1`, `$@`, `shift` | первый аргумент / все аргументы / «сдвинуть», чтобы следующий стал `$1` |
| `var=$(команда)` | записать вывод команды в переменную |
| `cat <<EOF ... EOF` | «heredoc»: вывести многострочный текст; `$переменные` внутри подставляются |
| `\$tun_ifs` | `\` не даёт bash подставить переменную, чтобы `$tun_ifs` попал в файл как есть для pf |
| `[[ условие ]]` | проверка; `-z` пустая строка, `-s` файл существует и не пустой, `=~` совпадение с шаблоном |
| `a \|\| b` | выполнить `b`, только если `a` не удался |
| `> файл`, `2>/dev/null` | записать вывод в файл / выбросить сообщения об ошибках |
| `exec sudo ...` | заменить текущий процесс тем же скриптом, но уже от root |

Если хотите посмотреть на всё вживую, после `--start` выполните `sudo cat /var/run/vpn-killswitch/rules.conf`. Там лежит именно тот конфиг, который читает pf, с комментариями.

Установка на комп встроена прямо в скрипты: один раз запускаете `--install` из папки со скриптом, и дальше команда `vpn-killswitch` работает из любой папки.

**macOS.** Установка:
```bash
sudo ./vpn-killswitch.sh --install
```
После этого из любой папки:
```bash
sudo vpn-killswitch --start 203.0.113.10
```
Скрипт копируется в `/usr/local/bin/vpn-killswitch`. Это папка из `PATH`, то есть из списка папок, где терминал ищет команды.

**Windows.** Установка:
```bat
vpn-killswitch.cmd --install
```
Скрипт копируется в `C:\Program Files\vpn-killswitch\`, а папка с запускалкой добавляется в системный `PATH`. Откройте **новое** окно терминала, и `vpn-killswitch --start ...` заработает из любой папки, в `cmd` и в PowerShell.

**Общее для обеих систем:**
- Устанавливается **копия**. Если вы поменяли скрипт в папке, запустите `--install` ещё раз, чтобы обновить её.
- Копию может менять только администратор. Скрипт запускается с правами администратора, поэтому подменить его не должна суметь ни одна обычная программа.
- Удаление — `--uninstall`. Если kill switch в этот момент включён, скрипт откажется удаляться и попросит сначала сделать `--stop`. Иначе можно остаться без интернета и без команды, которая его вернёт.

В README-windows я описал ещё вариант без установки: два ярлыка на рабочем столе, с `--start` и с `--stop`.

**Что проверено:**
- **macOS:** установку и удаление прогнал на тестовой копии в папке для временных файлов, без sudo. По-настоящему в `/usr/local/bin` ничего не ставил, это вы сделаете командой выше.
- **Windows:** по-прежнему не запускалась ни разу. Надо проверить на Windows, особенно изменение `PATH`.
